# FORGE 3D performance, battery and accessibility evaluation (Issue #4)

**Classification: EMULATION.** Everything here ran in headless Chromium 153 with **SwiftShader software WebGL** on a 4-core Xeon VM, using CDP CPU throttling for the "mobile" profile. **No physical phone was tested.** Absolute numbers are not device numbers. The comparisons (same harness, same synthetic models, baseline vs PR #2) are what this report relies on.

Targets measured:
- **PR #2** `design/forge-command-ui-20261108@1b474cd`, read-only worktree; nothing in it was edited.
- **Baseline**: `tools/performance/fixtures/stage.html`, the bare model-viewer stage with the same element ids. It separates viewer/model cost from interface cost.

Things that already work in PR #2:
- With the viewer CDN unreachable, the user gets a clear message.
- `touch-action="pan-y"` is set, so vertical page scrolling isn't captured by the 3D stage.
- The Motion toggle stops both the model and the ambient CSS (quiet in 3–5 s).
- Reduced motion turns off auto-rotate and all ambient CSS.
- The canvas render scale is 1.0 (mobile 1008×726 device px at DPR 3).
- No external requests other than the two pinned CDN files.
- The turntable is suppressed during authored turns.

## Measurement notes (what we learned not to trust)

- **CDP CPU throttling burns CPU.** At 4× it busy-waits the renderer (~85 % of a core, measured on the bare page). The harness therefore throttles **only** for timings (load, model-ready, fps) and switches it **off** for all CPU/battery readings.
- **Software GL lags behind.** After stopping motion or scrolling away, queued frames take 1–3 s to drain (up to 8 s and more for the heavy model at ~2 fps). Single averages mixed that lag with steady state. The harness now records 8 one-second windows, `seconds_to_quiet` (first window under 10 %) and the steady state (mean of the last 3).
- **A `requestAnimationFrame` probe forces frames itself.** It is used only while the model is animating, never for idle measurements.
- **CPU saturates on a 4-core host.** Software WebGL tops out near 380 %, so "animating CPU" hits that ceiling on every row. Use fps and the quiet-state readings instead.
- **"Offscreen" doesn't apply to PR #2's mobile layout.** The hero stage stays on screen across workspaces, so that column measures a stage that is still visible. It is reported but not used as a finding for PR #2.
- `turn_controls.tap_to_state_ms` in the committed PR #2 JSON was recorded before a harness fix and includes the 7.5 s observation window. Ignore that one field.

## Mobile performance budget (PROPOSED — owner to confirm)

| Metric | Budget | Basis |
| --- | --- | --- |
| LCP | ≤ 2.5 s | Core Web Vitals "good" threshold (web.dev) |
| CLS | ≤ 0.1, including model load and auto-restore | Core Web Vitals |
| INP | ≤ 200 ms | Core Web Vitals; needs a physical device |
| Long tasks before first interaction | none > 200 ms on mobile-emu | PROPOSED |
| Idle frames | 0 continuous frame production after ≤ 3 s with no interaction and Motion off **or** no model; harness idle steady CPU ≤ 5 % | PROPOSED, from the baseline (0 %) |
| Character asset | ≤ 100k triangles, ≤ 2048² textures (1024² preferred on mobile), GLB ≤ 10 MB | PROPOSED: heavy (200k / 2048² / 11 MB) needs 8.3–9.4 s to be ready on mobile-emu |
| Turn controls | `played_once` and `holds_end_pose` both true | functional gate |
| Fallbacks | no-WebGL and offline: user told within 3 s, no uncaught errors | functional gate |
| Animating fps | ≥ 30 fps on the owner's target Android phone | **physical device only**; emulation cannot answer this |

## Prioritized integration checklist for ChatGPT (PR #2 owns these files)

1. **P0 — Turn playback.** Await `view.updateComplete` before `play({repetitions:1})`, and remove the `currentTime` hold. Re-run `bench.mjs --checks`; `played_once` and `holds_end_pose` must both be true.
2. **P1 — Make ambient CSS motion finite.** Options:
   - give the intro animations a finite `animation-iteration-count`;
   - pause them (`animation-play-state: paused`) after ~10 s idle, or when the stage isn't the active view;
   - convert `forge-beat` from `box-shadow` to `opacity`/`transform`.

   Target: harness idle steady CPU ≤ 5 % with Motion **on**. Keep the existing Motion toggle and reduced-motion behaviour.
3. **P1 — Reserve the stage height** in the empty state (`min-height` or `aspect-ratio` on the deck), so loading or auto-restoring a model causes no shift. Target: mobile CLS ≤ 0.1.
4. **P1 — WebGL pre-check** before importing model-viewer (`canvas.getContext('webgl2') || canvas.getContext('webgl')`). Without it, show the existing non-model fallback with a plain message, and wrap the load so model-viewer's `TypeError` can't leave the status stuck.
5. **P2 — Lazy-load `html5-qrcode`** when the scanner is first opened. That's −375 KB raw on every launch.
6. **P2 — Fix `heading-order`**, then re-run axe.
7. **P3 — Optional:** split `index.html`'s inline script and styles into cacheable files.

## Physical-device checklist (owner; not done)

1. Android phone, Chrome, remote debugging. Use a synthetic `typical` model first, then the private model, in the private preview only.
2. Performance panel: launch to stage, load the model, play Idle for 30 s, tap each turn. Record the frame rate, long tasks and INP.
3. Battery: run 10 minutes on the stage screen with the screen on, in each of three states: (a) Motion on, (b) Motion off, (c) reduced motion. Record battery % and how warm the device feels.
4. Check that vertical scrolling over the stage still scrolls the page, and that pinch-zoom works.
5. Airplane mode after the first load: confirm the offline message.

- runs the generator tests and a one-run harness smoke test;
- checks that the npm copies are byte-identical to the live cdnjs/jsDelivr files (this sandbox couldn't reach those CDNs; GitHub runners can);
